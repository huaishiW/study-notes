# 1. 为什么需要异常处理

Web 项目运行过程中，不可能保证所有业务操作都能够正常完成。

例如修改员工信息时，如果数据库中的手机号字段存在唯一约束，而提交的数据使用了一个已经存在的手机号，就会违反数据库约束并产生异常。

此时服务器通常会返回：

```text
500 Internal Server Error
```

表示服务器内部发生异常。

如果项目没有专门处理这个异常，Spring Boot 会按照框架自身的默认方式返回错误信息。

问题在于：

> 框架默认返回的数据格式不一定符合项目自己的统一响应规范。

例如项目正常接口可能统一返回：

```java
Result
```

但是发生异常后，框架默认返回的 JSON 结构可能并不是 `Result`。

这样前端就无法按照原来的统一响应结构处理异常结果。

---

# 2. 异常处理要解决的核心问题

异常处理并不只是为了：

> 防止程序报错。

更重要的是：

> 当程序出现异常时，也能够按照项目统一的方式向前端返回结果。

例如正常请求返回：

```java
Result.success(...)
```

那么异常发生后，也希望返回：

```java
Result.error(...)
```

而不是让 Spring Boot 返回另外一种完全不同的 JSON 结构。

因此异常处理的重要目标之一是：

> 保证接口响应格式的一致性。

---

# 3. 三层架构中的异常传播

在常见三层架构中：

- Controller 负责接收请求和返回响应。
    
- Service 负责业务逻辑。
    
- Mapper 负责数据库访问。
    

假设 Mapper 操作数据库时发生异常，而当前方法没有处理异常，那么异常会继续向上抛出。

整个传播过程可以理解为：

```text
Mapper
  ↓
Service
  ↓
Controller
  ↓
Spring Boot 框架
```

也就是：

> 当前层没有处理异常，就会把异常交给调用它的上一层。

---

# 4. Mapper 中发生异常

假设：

```java
empMapper.update(emp);
```

执行数据库修改操作时违反了数据库约束。

Mapper 层产生异常。

如果 Mapper 自己没有处理：

> 异常就会抛给调用 Mapper 的 Service。

---

# 5. Service 中继续传播异常

Service 调用：

```java
empMapper.update(emp);
```

如果 Mapper 抛出了异常，而 Service 同样没有进行异常处理：

> Service 会继续将异常抛给 Controller。

因此异常并不会自动消失。

它会沿着方法调用关系逐层向上传播。

---

# 6. Controller 中继续传播异常

Controller 调用 Service：

```java
empService.update(emp);
```

如果 Service 抛出异常，而 Controller 仍然没有处理：

> 异常最终会继续交给 Spring Boot 框架。

Spring Boot 再按照自己的默认异常处理方式生成响应数据。

当前内容中描述的完整传播过程就是：

- Mapper 出错后抛给 Service。
    
- Service 再抛给 Controller。
    
- Controller 没有处理时继续抛给框架。
    
- 框架生成默认错误 JSON。
    

---

# 7. 默认异常响应存在的问题

Spring Boot 能够帮助我们处理未捕获异常，所以程序并不是完全没有响应。

但是框架生成的错误响应：

> 不一定符合当前项目自己的接口规范。

例如项目约定所有接口统一返回：

```java
Result
```

正常情况：

```java
return Result.success();
```

错误情况理想状态应该类似：

```java
return Result.error("操作失败");
```

但是默认异常响应不是由我们自己的 `Result` 创建。

因此会导致：

> 正常响应和异常响应的数据结构不统一。

---

# 8. 第一种方案：Controller 中使用 try...catch

一种直观的解决办法是：

> 在 Controller 中捕获异常。

例如：

```java
public Result update(@RequestBody Emp emp) {

    try {

        empService.update(emp);

        return Result.success();

    } catch (Exception e) {

        return Result.error("操作失败");

    }
}
```

这样确实可以解决当前接口的异常响应问题。

---

# 9. Controller 中使用 try...catch 的问题

问题在于：

> Controller 方法可能非常多。

例如：

```text
员工查询
员工新增
员工修改
员工删除
部门查询
部门新增
部门修改
部门删除
...
```

如果每个 Controller 方法都写：

```java
try {

    ...

} catch (Exception e) {

    ...

}
```

就会出现大量重复代码。

因此这种方式虽然可以工作，但是会造成：

> Controller 代码臃肿。

当前内容明确将“所有 Controller 的所有方法分别使用 `try...catch`”列为不推荐方案。

---

# 10. 为什么不应该在每个 Controller 重复处理

假设有 20 个 Controller 方法。

每个方法都需要：

```java
try {

    // 调用Service

} catch (Exception e) {

    return Result.error(...);

}
```

那么同样的异常处理逻辑会重复 20 次。

这些代码并不是每一个业务独有的逻辑，而是一种：

> 跨多个 Controller 都需要的公共处理逻辑。

因此更合理的方式是：

> 将公共异常处理逻辑集中起来。

这就是全局异常处理器存在的意义。

---

# 11. 全局异常处理

全局异常处理的核心思想是：

> Controller 中不再重复编写大量 `try...catch`，而是由一个统一的组件集中捕获和处理异常。

这样异常依然可以按照：

```text
Mapper
↓
Service
↓
Controller
```

向上传播。

但是到达 Web 层之后，会有统一的异常处理器负责捕获。

最终：

> 将异常转换成项目规定的统一响应结果。

当前内容将全局异常处理器作为推荐方案，因为这种方式更加简单、集中。

---

# 12. 全局异常处理器的基本结构

可以定义一个类：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

}
```

其中：

```java
@RestControllerAdvice
```

表示：

> 当前类用于进行全局异常处理。

当前内容中正是通过这个注解定义全局异常处理器。

---

# 13. @RestControllerAdvice

`@RestControllerAdvice` 的作用是：

> 标记一个全局异常处理类。

例如：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

}
```

添加这个注解后，可以在这个类中统一编写异常处理方法。

当前内容还给出了：

```text
@RestControllerAdvice
=
@ControllerAdvice
+
@ResponseBody
```

也就是说：

> 异常处理方法的返回值可以直接转换成响应数据返回给前端。

---

# 14. @ExceptionHandler

仅仅定义：

```java
@RestControllerAdvice
```

还不够。

还需要告诉 Spring：

> 发生某种异常之后，应该由哪个方法处理。

这就需要：

```java
@ExceptionHandler
```

例如：

```java
@ExceptionHandler
public Result ex(Exception e) {

    ...
}
```

其中方法参数：

```java
Exception e
```

表示该方法可以接收并处理对应异常。

当前内容指出，也可以通过 `@ExceptionHandler` 指定需要捕获的异常类型。

---

# 15. 基础全局异常处理器

完整示例：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    /**
     * 处理异常
     */
    @ExceptionHandler
    public Result ex(Exception e) {

        // 打印异常堆栈
        e.printStackTrace();

        // 返回统一错误结果
        return Result.error(
            "对不起,操作失败,请联系管理员"
        );
    }
}
```

这里完成了两个核心工作：

1. 捕获异常。
    
2. 将异常转换为统一的 `Result` 响应。
    

---

# 16. GlobalExceptionHandler

类名：

```java
GlobalExceptionHandler
```

本身只是一个普通类名。

真正让它具有全局异常处理能力的是：

```java
@RestControllerAdvice
```

例如：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

}
```

因此理解时不要认为：

> 只要类名叫 `GlobalExceptionHandler` 就可以处理异常。

真正起作用的是 Spring 提供的注解机制。

---

# 17. 异常处理方法

例如：

```java
@ExceptionHandler
public Result ex(Exception e) {

    ...
}
```

这个方法可以理解为：

> 异常处理入口。

当符合条件的异常出现时，Spring 会调用这个方法。

方法中的：

```java
Exception e
```

就是捕获到的异常对象。

---

# 18. 为什么方法需要接收 Exception

例如：

```java
public Result ex(Exception e)
```

这里：

```java
Exception e
```

代表发生的异常。

有了异常对象后，可以：

- 查看异常信息。
    
- 打印异常堆栈。
    
- 根据异常决定返回什么错误信息。
    

示例中使用：

```java
e.printStackTrace();
```

打印异常堆栈。

---

# 19. e.printStackTrace()

示例：

```java
e.printStackTrace();
```

用于：

> 打印异常的堆栈信息。

异常堆栈可以帮助开发人员了解：

- 异常是什么。
    
- 异常发生在哪里。
    
- 哪些方法调用最终导致异常。
    

因此它主要用于：

> 排查和定位程序错误。

---

# 20. 返回统一 Result

异常捕获之后：

```java
return Result.error(
    "对不起,操作失败,请联系管理员"
);
```

意味着：

> 即使程序内部发生异常，最终仍然按照项目统一的 `Result` 格式返回数据。

这解决了之前：

> Spring Boot 默认异常 JSON 与项目统一响应格式不一致

的问题。

---

# 21. 全局异常处理后的执行过程

假设数据库更新时发生异常。

整个过程可以理解为：

```text
Mapper执行数据库操作
        ↓
Mapper发生异常
        ↓
异常抛给Service
        ↓
Service继续向上抛
        ↓
Controller继续向上抛
        ↓
全局异常处理器捕获
        ↓
返回Result.error(...)
        ↓
转换成JSON
        ↓
前端接收并处理
```

最终前端收到的不再是框架默认错误结构，而是：

> 项目自己规定的统一响应结果。

---

# 22. 为什么异常仍然可以继续向上抛

引入全局异常处理后，并不意味着 Mapper 或 Service 必须把所有异常都捕获。

例如：

```java
empMapper.update(emp);
```

发生异常后，可以继续向上传播。

只要最终进入统一异常处理机制：

> 就可以集中处理。

这样可以避免在：

- Mapper
    
- Service
    
- Controller
    

每一层都重复写异常捕获代码。

---

# 23. @RestControllerAdvice 与 @ExceptionHandler 的职责

这两个注解需要区分。

## 23.1 @RestControllerAdvice

作用：

> 声明当前类是全局异常处理器。

使用位置：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

}
```

---

## 23.2 @ExceptionHandler

作用：

> 声明某个方法用于处理指定类型的异常。

使用位置：

```java
@ExceptionHandler
public Result ex(Exception e) {

}
```

因此可以记成：

```text
@RestControllerAdvice
负责定义“异常处理器是谁”

@ExceptionHandler
负责定义“异常由哪个方法处理”
```

当前内容最后也将这两个注解作为全局异常处理需要掌握的核心。

---

# 24. @RestControllerAdvice 与 @ResponseBody

当前内容给出了：

```text
@RestControllerAdvice
=
@ControllerAdvice
+
@ResponseBody
```

其中 `@ResponseBody` 的效果意味着：

> 异常处理方法返回的 Java 对象会作为响应数据返回，并转换为 JSON。

例如：

```java
return Result.error("操作失败");
```

最终返回给前端的是对应 JSON 数据，而不是跳转到某个页面。

---

# 25. 为什么全局异常处理适合 REST 接口

当前项目 Controller 使用：

```java
@RestController
```

接口通常需要返回 JSON。

因此发生异常后，同样希望返回：

```json
{
  "code": "...",
  "msg": "...",
  "data": null
}
```

这样的项目统一响应结构。

`@RestControllerAdvice` 正好可以让异常处理方法：

> 直接将返回对象转换成响应数据。

因此很适合 REST 风格接口的统一异常处理。

---

# 26. 全局异常处理器解决了哪些问题

## 26.1 避免重复 try...catch

Controller 不再需要大量：

```java
try {

} catch (Exception e) {

}
```

---

## 26.2 统一异常响应格式

所有异常最终都可以转换成：

```java
Result.error(...)
```

---

## 26.3 Controller 更专注于业务调用

Controller 可以继续保持：

```java
public Result update(@RequestBody Emp emp) {

    empService.update(emp);

    return Result.success();
}
```

不需要把大量异常处理逻辑混在业务流程中。

---

## 26.4 集中维护异常处理逻辑

以后需要修改异常提示时，可以集中修改：

```java
GlobalExceptionHandler
```

而不是修改很多 Controller 方法。

# 27. Controller 使用全局异常处理前后

## 27.1 分别捕获异常

```java
public Result update(@RequestBody Emp emp) {

    try {

        empService.update(emp);

        return Result.success();

    } catch (Exception e) {

        return Result.error("操作失败");

    }
}
```

Controller 同时承担：

- 请求处理。
    
- 业务调用。
    
- 异常处理。
    

---

## 27.2 使用全局异常处理

Controller：

```java
public Result update(@RequestBody Emp emp) {

    empService.update(emp);

    return Result.success();
}
```

统一异常处理器：

```java
@RestControllerAdvice

            "对不起,操作失败,请联系管理员"

```

职责更加集中。

# 28. 实际工程示例

假设数据库中的：

```text
phone
```

字段设置了唯一约束。

用户修改员工时提交：

```text
13309090027
```

但是数据库中已经存在相同手机号。

数据库操作发生异常。

如果没有全局异常处理：

> 异常最终交给 Spring Boot，返回框架默认错误 JSON。

如果存在：

```java
@RestControllerAdvice
public class GlobalExceptionHandler {

    @ExceptionHandler
    public Result ex(Exception e) {

        e.printStackTrace();

        return Result.error(
            "对不起,操作失败,请联系管理员"
        );
    }
}
```

那么异常最终会被统一捕获，并返回项目定义的错误结果。

前端就能够按照正常的响应结构解析错误信息并进行提示。

# 29. 全局异常处理的核心思想

学习这一部分时，真正需要理解的不是只记两个注解，而是：

> 把分散在各个 Controller 中重复出现的异常处理逻辑提取出来，交给一个统一组件集中处理。

这体现的是一种：

> 公共逻辑集中管理

的思想。

Controller 继续负责正常业务请求。

异常处理器专门负责异常。

两者职责分离之后，代码更加清晰。

# 30. 常见误区

## 30.1 有全局异常处理器后程序不会发生异常

错误。

异常仍然会发生。

全局异常处理解决的是：

> 异常发生之后如何统一处理。

而不是：

> 消除异常。

---

## 30.2 Mapper 出现异常后会直接被全局处理器捕获

更准确地说，异常通常会沿调用关系：

```text
Mapper
→ Service
→ Controller
```

不断向上传播。

当 Web 请求处理过程中异常最终没有被业务代码处理时，再进入统一异常处理机制。

---

## 30.3 每个 Controller 仍然必须写 try...catch

不是。

引入全局异常处理的重要原因之一，就是减少这种重复异常捕获代码。

---

## 30.4 @ExceptionHandler 定义全局异常处理类

错误。

定义全局异常处理类主要使用：

```java
@RestControllerAdvice
```

而：

```java
@ExceptionHandler
```

主要用于定义：

> 哪个方法处理哪种异常。

---

## 30.5 全局异常处理只是打印异常

不是。

打印：

```java
e.printStackTrace();
```

只是示例中的一个操作。

更关键的是：

```java
return Result.error(...);
```

也就是：

> 将异常转换成项目统一响应结果。

---

# 31. 学习重点

## 31.1 基础

需要掌握：

- 为什么 Web 项目需要异常处理。
    
- 500 状态表示服务器端异常。
    
- 未处理异常如何在三层架构中传播。
    
- 为什么框架默认异常响应可能不符合项目统一响应规范。
    

## 31.2 两种异常处理方案

需要理解：

### Controller 分别 try...catch

问题：

> 重复代码多，Controller 容易臃肿。

### 全局异常处理

优势：

> 集中、统一、更加容易维护。

---

## 31.3 核心注解

需要重点掌握：

```java
@RestControllerAdvice
```

作用：

> 声明全局异常处理器。

以及：

```java
@ExceptionHandler
```

作用：

> 指定异常处理方法。

---

## 31.4 重点理解

需要重点理解：

- Mapper、Service、Controller 之间异常如何向上传播。
    
- 为什么不能依赖 Spring Boot 默认错误响应。
    
- 全局异常处理为什么能够减少重复 `try...catch`。
    
- 为什么异常结果也应该遵守统一响应结构。
    
- `@RestControllerAdvice` 与 `@ExceptionHandler` 的职责区别。
    
- 全局异常处理本质上为什么属于公共异常逻辑的集中管理。
    

> [!tip] 一句话总结
> 
> 在三层架构中，未处理异常会从 Mapper 逐层向 Service、Controller 和框架传播，而框架默认生成的错误响应可能不符合项目统一响应规范；通过 `@RestControllerAdvice` 定义全局异常处理器，并使用 `@ExceptionHandler` 统一捕获异常，可以避免在每个 Controller 中重复编写 `try...catch`，并将异常统一转换成 `Result.error(...)` 返回给前端。
