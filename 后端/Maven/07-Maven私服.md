>[!abstract]
> Maven 私服是企业 Maven 项目中的内部远程仓库，主要解决**团队之间的 Maven 资源共享**以及**第三方依赖统一代理**问题。

---

# 1. 为什么需要 Maven 私服

在多模块项目中，一个模块可以被其他模块依赖。

但如果两个模块属于**不同项目组甚至不同开发团队**，仅仅依赖本地 Maven 仓库是不够的。

例如：

- 团队 A 开发 `tlias-utils`
- A 将其安装到了自己的本地仓库
- 团队 B 希望使用 `tlias-utils`

B 的 Maven 无法访问 A 的本地仓库。

即使 B 的 Maven 会访问中央仓库，中央仓库也不存在公司自己开发的 `tlias-utils`。

因此需要一个公司内部所有项目都能够访问的 Maven 仓库。

这就是 **Maven 私服**。

---

# 2. 什么是 Maven 私服

**Maven 私服（Private Repository）**：

> 部署在企业内部网络中的 Maven 远程仓库服务，用于存储企业内部开发的 Maven 资源，同时可以代理外部 Maven 仓库。

它主要承担两个职责：

## 2.1 企业内部资源共享

公司开发的：

- 公共工具类
- 公共组件
- 公共模块
- 内部依赖

可以发布到私服。

其他项目只需要根据 Maven 坐标声明依赖即可。

## 2.2 第三方依赖代理

如果项目需要使用第三方依赖，而本地仓库中不存在：

- Maven 可以从私服获取
- 如果私服没有对应依赖，私服可以继续从中央仓库获取
- 获取后私服可以保存该资源，供公司内部其他项目使用 

因此私服实际上也是企业 Maven 依赖体系中的一个中间层。

---

# 3. Maven 依赖查找体系

在企业私服的场景中，依赖查找可以理解为：

| 顺序  | 仓库   | 作用                |
| --- | ---- | ----------------- |
| 1   | 本地仓库 | 优先查找本机已有依赖        |
| 2   | 私服   | 获取企业内部资源或代理的第三方资源 |
| 3   | 中央仓库 | 私服没有资源时获取第三方依赖    |

需要注意：

> **私服不是中央仓库的替代品，而是企业内部 Maven 资源与外部中央仓库之间的中间仓库。**

---

# 4. Maven 私服中的仓库类型

私服主要涉及三类仓库：

| 仓库         | 用途                 |
| ---------- | ------------------ |
| `RELEASE`  | 存储企业发布的正式版本        |
| `SNAPSHOT` | 存储企业开发中的快照版本       |
| `Central`  | 存储从中央仓库代理/下载的第三方依赖 |

## RELEASE

用于功能稳定、可以正式发布的版本。

例如：

```text
tlias-utils:1.0
```

## SNAPSHOT

用于开发过程中的版本。

例如：

```text
tlias-utils:1.0-SNAPSHOT
```

因此：

> **版本号中的 `SNAPSHOT` 不只是一个命名习惯，它决定了资源发布到私服时使用的仓库类型。**

其中 RELEASE 与 SNAPSHOT 分别对应正式发布版本和开发中的快照版本。

---

# 5. Maven 私服的核心工作模式

私服可以同时处理两类资源：

## 企业内部资源

公司自己的模块：

```text
项目 A
  ↓
发布内部模块
  ↓
Maven 私服
  ↓
项目 B / 项目 C 使用
```

## 外部第三方资源

第三方依赖：

```text
项目
  ↓
私服
  ↓
中央仓库
```

因此从企业角度看，私服实际上统一了 Maven 资源的访问入口。

# 6. Maven 私服的资源发布

项目开发完成后，可以通过 Maven 的：

```bash
mvn deploy
```

将 Maven 资源发布到私服。

## 6.1 发布需要解决的问题

发布之前主要需要配置：

| 配置     | 位置             | 作用         |
| ------ | -------------- | ---------- |
| 用户名、密码 | `settings.xml` | 身份认证       |
| 私服访问地址 | `settings.xml` | Maven 获取依赖 |
| 发布地址   | `pom.xml`      | Maven 发布资源 |

其中项目的发布地址通常通过：

```xml
<distributionManagement>
    <repository>
        ...
    </repository>

    <snapshotRepository>
        ...
    </snapshotRepository>
</distributionManagement>
```

进行配置。

---

# 7. `settings.xml` 与 `pom.xml` 在私服中的职责

这一部分可以和前面 Maven 配置知识联系起来。

## `settings.xml`

主要描述：

> **当前 Maven 环境如何连接私服。**

其中涉及：

```xml
<servers>
```

用于保存私服访问认证信息。

```xml
<mirrors>
```

用于配置 Maven 的镜像仓库。

```xml
<profiles>
```

用于配置仓库及其使用规则，例如是否允许获取 SNAPSHOT。

## `pom.xml`

主要描述：

> **当前项目应该把构建产物发布到哪里。**

使用：

```xml
<distributionManagement>
```

分别指定：

- RELEASE 发布地址
- SNAPSHOT 发布地址    

因此可以继续沿用前面的核心区分：

> `settings.xml` → Maven 环境配置  
> `pom.xml` → 项目配置

# 8. `deploy` 与 `install` 的区别

Part 07 已经出现过 `install`，这里需要建立两者的联系。

| 生命周期阶段    | 主要作用             |
| --------- | ---------------- |
| `install` | 将构建产物安装到**本地仓库** |
| `deploy`  | 将构建产物发布到**远程私服** |

可以把它理解为 Maven 资源的两个不同存储层级：

```text
install → 本地仓库
deploy  → 私服
```

因此：

> **`install` 主要解决本机项目之间的依赖使用；`deploy` 主要解决团队/项目之间的资源共享。**

# 9. Maven 私服与多模块开发

Part 6 中我们学习了：

> 多模块项目可以将公共模块独立出来。

例如：

```text
tlias-pojo
tlias-utils
tlias-web-management
```

如果这些公共模块只在同一个 Maven 工程内部使用，那么模块依赖和聚合就可以解决问题。

但如果：

- 项目 A 需要使用公共模块
- 项目 B 也需要使用公共模块
- 项目 C 同样需要使用公共模块

这时就需要将公共模块发布到 Maven 私服。

因此：

> **多模块解决“一个项目内部如何组织模块”，私服解决“多个项目之间如何共享 Maven 资源”。**

这是 Part 07 和 Part 08 最重要的联系。

---

# 10. 私服的核心价值

Maven 私服主要解决三个问题：

## ① 企业内部依赖共享

公司自己开发的 Maven 模块可以作为标准依赖被其他项目使用。

## ② 统一依赖入口

企业项目可以统一通过私服获取第三方依赖，而不需要每个项目直接访问外部中央仓库。

## ③ Maven 资源集中管理

企业内部发布的：

- RELEASE
- SNAPSHOT

都可以由私服统一管理。

因此：

> **私服本质上是企业 Maven 依赖体系中的资源中心。**

# 13. 核心记忆

>[!tips]
> **本地仓库**解决“我的电脑上有没有”。
> **中央仓库**提供公共的第三方 Maven 资源。
> **私服**解决“公司内部项目之间如何共享 Maven 资源”，同时可以代理中央仓库。
> **`install`** 将资源安装到本地仓库。
> **`deploy`** 将资源发布到远程私服。
> **`dependencies`** 决定项目实际使用哪些依赖。
> **`dependencyManagement`** 决定这些依赖统一使用什么版本。

最终可以把 Maven 多模块与私服的关系理解为：

> **多模块解决项目内部的模块化，私服解决项目之间的资源共享。**
