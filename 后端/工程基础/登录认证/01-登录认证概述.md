# 1. 什么是登录认证

在后台管理系统中，并不是所有用户都可以直接访问系统中的业务功能。

通常需要先完成登录：

- 用户输入用户名和密码
    
- 服务端校验用户名和密码是否正确
    
- 校验成功后允许用户进入系统
    
- 校验失败则拒绝登录
    

材料中的登录功能就是根据用户名和密码判断员工身份是否合法：

> 用户名和密码都正确，则登录成功；否则登录失败。

但是，仅仅完成用户名和密码校验，还不能算真正完成了整个登录认证功能。

# 2. 为什么完成登录功能后仍然不安全

在基础登录功能完成后，用户输入正确的用户名和密码可以正常进入后台系统。

但是材料随后发现一个问题：

> 即使用户没有执行登录操作，直接访问后台系统地址，仍然可以访问系统中的部门管理、员工管理等功能。

出现这个问题的原因是：

> 服务端的业务接口并没有判断当前请求对应的用户是否已经登录。

也就是说：

```text
/login
```

虽然完成了用户名和密码验证，但是其他接口仍然没有任何访问限制。

因此：

> **登录成功只是完成了身份验证的第一步，后续每一次业务请求仍然需要进行登录状态校验。**

# 3. 登录与登录校验的区别

登录和登录校验解决的是两个不同的问题。

## 3.1 登录

登录主要解决：

> **当前输入用户名和密码的人是谁，他提供的身份凭证是否正确？**

例如：

```text
username = admin
password = 123456
```

服务端根据用户名和密码查询员工信息。

如果能够查询到员工：

> 登录成功。

如果查询不到：

> 登录失败。

---

## 3.2 登录校验

登录校验主要解决：

> **当前正在访问业务接口的人，之前是否已经成功登录？**

例如用户访问：

```text
/depts
/emps
```

服务端需要先判断：

> 当前请求是否来自一个已经登录成功的用户。

如果已经登录：

> 继续执行正常业务。

如果没有登录：

> 拒绝访问，并返回错误结果。

材料将这种过程称为：

**登录校验。**

# 4. 为什么服务端不知道用户之前是否登录

登录认证中最核心的一个问题来自 HTTP 协议。

HTTP 是：

> **无状态协议。**

所谓无状态，材料中的解释是：

> 每一次请求都是独立的，下一次请求不会自动携带上一次请求产生的状态数据。

例如用户第一次发送请求：

```text
POST /login
```

登录成功。

之后又发送：

```text
GET /depts
```

对于服务端来说，这两次请求本身是相互独立的。

如果没有额外机制，第二次请求并不能让服务器自动知道：

> 这个用户刚才已经登录成功了。

因此，HTTP 无状态是登录认证必须解决的核心问题之一。

# 5. 登录认证需要解决的两个问题

材料将登录校验的整体实现思路概括成两个部分。

## 5.1 保存登录成功的标记

用户登录成功之后，需要保存一个：

> **用户已经成功登录的身份标记。**

以后用户再次访问业务接口时，可以通过这个标记判断用户身份。

材料中的原始描述是：

> 员工登录成功后，需要将用户登录成功的信息存储起来，记录用户已经登录成功的标记。

## 5.2 后续请求统一进行校验

用户访问其他业务接口时，服务端需要：

> 在业务方法执行之前统一检查登录标记。

如果存在合法登录标记：

> 请求放行。

如果不存在合法登录标记：

> 拒绝请求。

因此，登录认证本质上需要同时解决：

```text
如何保存用户登录状态

如何在后续请求中统一校验用户登录状态
```

# 6. 为什么需要统一登录校验

系统中的很多业务接口都需要登录之后才能访问。

例如：

- 查询部门
    
- 新增部门
    
- 删除部门
    
- 修改部门
    
- 查询员工
    
- 新增员工
    
- 修改员工
    

如果在每一个 Controller 方法中都手动编写：

```java
if (用户未登录) {
    return Result.error(...);
}
```

那么相同的登录校验逻辑会重复出现。

材料也指出，如果每一个查询、删除、添加、修改功能都重复进行登录校验，会导致代码十分繁琐。

因此，需要使用：

> **统一拦截技术**

将登录校验逻辑集中处理。

# 7. 登录认证涉及的两类核心技术

材料将完整登录校验需要使用的技术分为两类：

## 7.1 会话技术

会话技术用于解决：

> 用户登录成功之后，后续请求如何继续携带或获取登录身份标记。

材料中涉及的会话跟踪方案包括：

```text
Cookie
Session
令牌技术
```

## 7.2 统一拦截技术

统一拦截技术负责：

> 在业务接口真正执行之前统一拦截请求并进行登录校验。

材料中介绍了两种实现方式：

```text
Filter
Interceptor
```

因此，可以把完整登录认证理解为：

> **会话跟踪负责证明“我是谁”，统一拦截负责检查“你有没有资格继续访问”。**

# 8. 登录认证的整体过程

完整登录认证过程可以分成两个阶段。

## 8.1 登录阶段

用户首先提交：

```text
用户名
密码
```

服务端进行身份校验。

如果验证失败：

> 登录失败。

如果验证成功：

> 生成或保存一个能够代表当前用户身份的登录标记，并返回给客户端。

## 8.2 后续访问阶段

用户继续访问业务接口时：

> 客户端需要携带之前获得的身份标记。

服务端统一拦截请求，对身份标记进行校验。

如果身份合法：

> 放行请求，继续执行业务。

如果身份不合法：

> 拒绝请求，要求用户重新登录。

# 9. Token 在登录认证中的作用

材料最终采用的是：

**令牌技术**

来维护登录状态。

令牌本质上是：

> 用户身份的标识。

用户登录成功后，服务器生成令牌并返回给前端。

之后：

- 前端保存令牌
    
- 每次请求携带令牌
    
- 服务端校验令牌
    
- 合法则放行
    
- 非法则拒绝
    

材料也明确指出，JWT 登录认证最终包含两个核心动作：

1. 登录成功之后生成令牌。
    
2. 后续请求中接收并校验令牌。
    

具体的 Token 和 JWT 原理会在后续单独整理。

# 10. 登录认证与权限控制的区别

当前材料主要解决的是：

> 用户是否已经登录。

也就是：

**认证 Authentication**

当前阶段暂时不解决：

> 登录后的用户是否有权限执行某个具体操作。

例如：

```text
普通员工能不能删除员工
管理员能不能修改部门
```

这些属于进一步的：

**权限控制 / 授权 Authorization**

因此，当前这一部分重点仍然是：

> 确认用户身份，并保证未登录用户不能访问受保护接口。

# 11. 当前阶段需要掌握的核心内容

1. 登录功能主要负责验证用户名和密码是否正确。
    
2. 登录成功并不意味着后续所有接口已经具备安全保护。
    
3. 登录校验负责判断当前请求对应的用户是否已经成功登录。
    
4. HTTP 是无状态协议，不同请求之间默认不会共享登录状态。
    
5. 登录认证需要保存登录成功后的身份标记。
    
6. 后续每一次请求都需要携带或能够获得这个身份标记。
    
7. 服务端需要在业务接口执行之前统一进行登录校验。
    
8. 会话技术负责在多次请求之间维护用户身份状态。
    
9. Filter 和 Interceptor 可以用于统一拦截请求。
    
10. 当前材料最终使用令牌技术实现登录认证。
    
11. JWT 登录认证主要包括“登录成功生成令牌”和“后续请求校验令牌”两个步骤。
    
12. 登录认证解决的是“你是谁以及是否已登录”，权限控制解决的是“你登录之后能做什么”。
    

> [!tip] 一句话总结
> 
> `登录认证不仅要在登录时验证用户名和密码，还需要解决 HTTP 无状态导致的登录状态无法自动延续问题，通过会话跟踪保存用户身份，并在后续请求中统一进行登录校验。`
