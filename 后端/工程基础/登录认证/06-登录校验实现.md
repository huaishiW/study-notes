# 1. 为什么还需要登录校验

前面已经完成了 JWT 登录认证：

- 用户提交用户名和密码
    
- 服务端验证用户身份
    
- 登录成功后生成 JWT
    
- JWT 返回给前端
    
- 前端保存 JWT
    
- 后续请求携带 JWT
    

但是，仅仅让客户端携带 Token 还不够。

服务端还必须在业务接口执行之前判断：

> **当前请求携带的 JWT 是否存在并且是否合法。**

只有校验成功之后，才能允许用户访问后台业务接口。

因此，登录认证最后还需要完成：

**统一登录校验。**

材料中最终分别使用 Filter 和 Interceptor 演示了这一功能。

# 2. 登录校验的核心规则

登录校验主要需要解决两个问题。

## 2.1 所有请求都需要校验吗

不是。

材料中明确指出：

> **登录请求例外。**

因为用户访问：

```text
/login
```

本身就是为了完成登录。

如果登录接口也要求先携带合法 Token，就无法完成首次登录。

因此：

```text
/login
```

需要直接放行。

## 2.2 什么情况下可以访问业务接口

只有同时满足：

```text
存在 Token
Token 校验通过
```

才可以继续访问业务接口。

否则：

> 返回未登录结果，不继续放行业务请求。

# 3. 登录校验的统一流程

材料将登录校验整理成六个步骤：

1. 获取请求 URL。
    
2. 判断 URL 是否包含 `login`，如果是登录请求则直接放行。
    
3. 获取请求头中的 Token。
    
4. 判断 Token 是否存在，不存在则响应 `401`。
    
5. 解析 JWT，解析失败则响应 `401`。
    
6. Token 合法则放行。
    

这六步就是整个登录校验的核心逻辑。

# 4. 为什么先判断登录请求

用户第一次登录时还没有 JWT。

如果登录接口也执行：

```text
获取 Token
校验 Token
```

那么第一次登录必然失败。

因此统一登录校验中首先需要识别：

```text
/login
```

请求。

如果是登录请求：

> 直接放行，不执行 JWT 校验。

# 5. 获取请求中的 Token

前面已经知道，当前项目中的前端会把 JWT 放在请求头：

```text
token
```

中。

因此服务端可以通过：

```java
String jwt = request.getHeader("token");
```

读取 Token。

这里获得的：

```java
jwt
```

就是前端登录成功后保存并在后续请求中携带的 JWT。

# 6. 判断 Token 是否存在

获取请求头后，需要先判断：

```java
jwt
```

是否为空。

材料中使用：

```java
StringUtils.hasLength(jwt)
```

进行判断。

例如：

```java
if (!StringUtils.hasLength(jwt)) {

    response.setStatus(
            HttpStatus.SC_UNAUTHORIZED
    );

    return;
}
```

如果没有携带 JWT：

> 当前用户不能通过登录校验。

# 7. 为什么返回 401

材料中登录校验失败时设置：

```java
response.setStatus(
        HttpStatus.SC_UNAUTHORIZED
);
```

也就是：

```text
HTTP 401
```

表示当前请求：

> 未通过身份认证。

因此当前案例中：

```text
没有 Token
Token 非法
```

都会返回：

```text
401
```

# 8. 校验 JWT

Token 存在并不意味着 Token 一定合法。

还需要通过：

```java
JwtUtils.parseJWT(jwt);
```

解析 JWT。

材料中的写法：

```java
try {

    JwtUtils.parseJWT(jwt);

} catch (Exception e) {

    response.setStatus(
            HttpStatus.SC_UNAUTHORIZED
    );

    return;
}
```

如果 JWT：

- 被篡改
    
- 已经过期
    
- 签名不匹配
    
- 无法正常解析
    

`parseJWT()` 就会抛出异常。

此时认为：

> JWT 校验失败。

# 9. Token 合法后放行

如果：

```text
Token 存在
JWT 解析成功
```

说明当前 Token 合法。

此时才允许请求继续访问后面的业务资源。

Filter 中通过：

```java
chain.doFilter(request, response);
```

完成放行。

# 10. 使用 Filter 实现登录校验

材料中首先使用：

```java
TokenFilter
```

实现完整登录校验。

基本结构：

```java
@Slf4j
@WebFilter(urlPatterns = "/*")
public class TokenFilter implements Filter {

    @Override
    public void doFilter(
            ServletRequest req,
            ServletResponse resp,
            FilterChain chain)
            throws IOException, ServletException {

    }
}
```

其中：

```java
@WebFilter(urlPatterns = "/*")
```

表示：

> Filter 拦截所有请求。

然后在：

```java
doFilter()
```

中完成 JWT 登录校验。

# 11. 将请求转换为 HttpServletRequest

Filter 接收到的是：

```java
ServletRequest
ServletResponse
```

材料中将其转换成：

```java
HttpServletRequest request =
        (HttpServletRequest) req;

HttpServletResponse response =
        (HttpServletResponse) resp;
```

这样才能继续使用：

```java
getRequestURL()
getHeader()
setStatus()
```

等 HTTP 请求与响应相关方法。

# 12. Filter 中识别登录请求

首先获取 URL：

```java
String url =
        request.getRequestURL().toString();
```

然后判断：

```java
if (url.contains("login")) {

    chain.doFilter(request, response);

    return;
}
```

如果当前是登录请求：

> 直接放行并结束当前登录校验逻辑。

# 13. Filter 中获取并校验 Token

对于普通业务请求：

```java
String jwt =
        request.getHeader("token");
```

先获取 JWT。

如果 JWT 不存在：

```java
if (!StringUtils.hasLength(jwt)) {

    response.setStatus(
            HttpStatus.SC_UNAUTHORIZED
    );

    return;
}
```

然后继续：

```java
try {
    JwtUtils.parseJWT(jwt);
} catch (Exception e) {

    response.setStatus(
            HttpStatus.SC_UNAUTHORIZED
    );

    return;
}
```

只有两步都通过，才能继续放行。

# 14. TokenFilter 完整实现

当前材料中的核心代码可以整理为：

```java
@Slf4j
@WebFilter(urlPatterns = "/*")
public class TokenFilter implements Filter {

    @Override
    public void doFilter(
            ServletRequest req,
            ServletResponse resp,
            FilterChain chain)
            throws IOException, ServletException {

        HttpServletRequest request =
                (HttpServletRequest) req;

        HttpServletResponse response =
                (HttpServletResponse) resp;

        // 1. 获取请求 URL
        String url =
                request.getRequestURL().toString();

        // 2. 登录请求直接放行
        if (url.contains("login")) {
            chain.doFilter(request, response);
            return;
        }

        // 3. 获取 Token
        String jwt =
                request.getHeader("token");

        // 4. Token 不存在
        if (!StringUtils.hasLength(jwt)) {
            response.setStatus(
                    HttpStatus.SC_UNAUTHORIZED
            );
            return;
        }

        // 5. 校验 Token
        try {
            JwtUtils.parseJWT(jwt);
        } catch (Exception e) {
            response.setStatus(
                    HttpStatus.SC_UNAUTHORIZED
            );
            return;
        }

        // 6. Token 合法，放行
        chain.doFilter(request, response);
    }
}
```

# 15. Filter 方案中的三种结果

Filter 登录校验最终会产生三种主要情况。

## 15.1 登录请求

```text
/login
```

结果：

> 直接放行。

## 15.2 普通请求但 Token 不合法

包括：

```text
没有 Token
Token 解析失败
```

结果：

```text
401
```

并且：

> 不继续放行。

## 15.3 Token 合法

结果：

> 放行并执行业务接口。

# 16. 使用 Interceptor 实现登录校验

材料后面又使用：

```java
TokenInterceptor
```

重新实现了一次相同的登录校验逻辑。

材料明确指出：

> Interceptor 中的登录校验业务逻辑和 Filter 基本一致，只是技术方案由 Filter 换成了 Interceptor。

# 17. TokenInterceptor

Interceptor 实现：

```java
HandlerInterceptor
```

并把登录校验写在：

```java
preHandle()
```

中。

例如：

```java
@Slf4j
@Component
public class TokenInterceptor
        implements HandlerInterceptor {

    @Override
    public boolean preHandle(
            HttpServletRequest request,
            HttpServletResponse response,
            Object handler)
            throws Exception {

    }
}
```

# 18. Interceptor 中识别登录请求

同样先获取：

```java
String url =
        request.getRequestURL().toString();
```

如果 URL 中包含：

```text
login
```

则：

```java
return true;
```

表示直接放行登录请求。

# 19. Interceptor 中获取 Token

通过：

```java
String jwt =
        request.getHeader("token");
```

获取 JWT。

如果为空：

```java
if (!StringUtils.hasLength(jwt)) {

    response.setStatus(
            HttpStatus.SC_UNAUTHORIZED
    );

    return false;
}
```

这里和 Filter 的最大区别是：

> Interceptor 通过返回 `false` 阻止请求继续执行。

# 20. Interceptor 中校验 JWT

继续调用：

```java
JwtUtils.parseJWT(jwt);
```

解析 JWT。

如果出现异常：

```java
catch (Exception e) {

    response.setStatus(
            HttpStatus.SC_UNAUTHORIZED
    );

    return false;
}
```

说明 Token 校验失败。

如果解析成功：

```java
return true;
```

表示放行。

材料中的 `TokenInterceptor` 最终正是按照这个逻辑实现。

# 21. 注册 TokenInterceptor

自定义 Interceptor 还需要注册到 Spring MVC。

例如：

```java
@Configuration
public class WebConfig
        implements WebMvcConfigurer {

    @Autowired
    private TokenInterceptor tokenInterceptor;

    @Override
    public void addInterceptors(
            InterceptorRegistry registry) {

        registry.addInterceptor(
                tokenInterceptor
        ).addPathPatterns("/**");
    }
}
```

材料中就是通过这种方式让：

```java
TokenInterceptor
```

真正参与请求处理。

# 22. 登录接口的另一种排除方式

在前面的 Interceptor 机制中已经学到，可以通过：

```java
excludePathPatterns()
```

直接排除登录接口。

例如：

```java
registry.addInterceptor(tokenInterceptor)
        .addPathPatterns("/**")
        .excludePathPatterns("/login");
```

材料在 Interceptor 详解中明确演示了这种配置方式。

这样就可以在配置层明确表达：

> 所有请求都进行登录校验，但 `/login` 除外。

# 23. Filter 与 Interceptor 登录校验的相同点

两种方案的核心业务逻辑基本一致。

都需要完成：

```text
识别登录请求
获取 Token
判断 Token 是否存在
解析 JWT
校验失败返回 401
校验成功放行
```

因此真正变化的是：

> 拦截请求的技术实现。

而不是登录校验本身的业务规则。

# 24. Filter 与 Interceptor 的放行方式

Filter 使用：

```java
chain.doFilter(request, response);
```

表示：

> 放行。

Interceptor 使用：

```java
return true;
```

表示：

> 放行。

因此可以简单对比：

|方案|放行|拒绝|
|---|---|---|
|Filter|`chain.doFilter()`|不调用 `doFilter()`，直接 `return`|
|Interceptor|`return true`|`return false`|

# 25. 两种方案是否需要同时使用

材料明确指出：

> 登录校验 Filter 和登录校验 Interceptor 只需要使用其中一种即可。

因此：

```text
Filter 登录校验
```

和：

```text
Interceptor 登录校验
```

是当前案例中的：

**两种可选实现方案**

而不是必须同时启用的两个步骤。

# 26. 完整 JWT 登录认证链路

经过前面的所有内容，现在完整登录认证已经形成。

## 26.1 登录阶段

用户提交：

```text
用户名
密码
```

服务端校验成功后：

```text
生成 JWT
返回 JWT 给前端
```

前端保存 JWT。

## 26.2 后续请求阶段

客户端访问业务接口时：

```text
请求头携带 JWT
```

服务端通过 Filter 或 Interceptor 统一拦截请求。

然后：

- 登录请求 → 直接放行
    
- Token 不存在 → 返回 401
    
- Token 解析失败 → 返回 401
    
- Token 合法 → 放行业务请求
    

这才形成完整的：

**JWT 登录认证流程。**

# 27. 当前登录校验解决了什么问题

在没有登录校验之前：

> 用户即使没有登录，也能够直接访问后台业务接口。

增加统一 JWT 登录校验之后：

未登录用户访问后台：

> 登录校验失败，前端根据错误结果跳转到登录页面。

已经登录并携带合法 JWT 的用户：

> 登录校验成功，可以正常访问业务功能。

材料分别对 Filter 和 Interceptor 方案进行了这两种情况的测试。

# 28. 当前阶段需要掌握的核心内容

1. JWT 返回给前端后，服务端还必须对后续请求进行统一登录校验。
    
2. 登录接口本身不需要 JWT 校验，必须允许未登录用户访问。
    
3. 普通业务请求需要从请求头 `token` 中获取 JWT。
    
4. Token 不存在时，当前材料返回 HTTP `401`。
    
5. Token 存在后，还需要调用 `JwtUtils.parseJWT()` 进行解析校验。
    
6. JWT 解析失败时，同样返回 `401`。
    
7. JWT 解析成功说明 Token 合法，可以继续访问业务接口。
    
8. Filter 可以通过 `TokenFilter` 实现登录校验。
    
9. Filter 通过 `chain.doFilter()` 放行。
    
10. Filter 拒绝请求时不再调用 `chain.doFilter()`。
    
11. Interceptor 可以通过 `TokenInterceptor` 实现相同登录校验逻辑。
    
12. Interceptor 的登录校验通常写在 `preHandle()` 中。
    
13. Interceptor 返回 `true` 表示放行，返回 `false` 表示拒绝请求。
    
14. Interceptor 需要通过 `WebMvcConfigurer` 注册。
    
15. 可以通过 `excludePathPatterns("/login")` 排除登录接口。
    
16. Filter 与 Interceptor 是两种登录校验实现方案，当前案例只需要选择其中一种。
    
17. 完整 JWT 登录认证由“登录生成 Token”和“后续请求统一校验 Token”共同组成。
    

> [!tip] 一句话总结
> 
> `JWT登录校验通过统一拦截后续请求，放行登录接口，并对普通请求中的 Token 进行存在性和合法性校验：无 Token 或解析失败返回 401，Token 合法则通过 Filter 或 Interceptor 放行业务请求。`
