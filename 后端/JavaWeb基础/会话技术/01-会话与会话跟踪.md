# 1. 什么是会话

在 Web 开发中，会话指的是：

> **浏览器与服务器之间的一次连接过程。**

当用户打开浏览器并第一次访问服务器时，会话开始建立。

在这次会话结束之前，浏览器可以向服务器发送多次请求。

例如：

```text
第一次请求：登录
第二次请求：查询部门
第三次请求：查询员工
```

只要浏览器和服务器之间的这次连接关系没有结束，这些请求都属于同一次会话。

# 2. 一次会话可以包含多次请求

一次会话并不等于一次 HTTP 请求。

在同一个浏览器中，用户可能连续执行很多操作。

例如：

```text
登录系统
查询部门
新增员工
修改员工
```

这些操作会产生多次 HTTP 请求。

但从用户访问服务器这一整个过程来看，它们仍然可以属于同一次会话。

因此：

> **一次会话中可以包含多次请求和响应。**

# 3. 会话与浏览器有关

材料中指出：

> 会话与浏览器相关。

例如同时有三个浏览器访问同一个服务器，那么就会存在三个不同的会话。

同一个浏览器在未结束会话之前多次访问服务器，这些请求属于同一个会话。

因此可以理解为：

```text
不同浏览器
→ 不同会话

同一浏览器连续访问
→ 可以属于同一会话
```

# 4. 什么是会话跟踪

服务器会同时接收到大量请求。

但是服务器需要判断：

> **这些请求是不是来自同一个浏览器。**

如果多个请求来自同一个浏览器，就可以认为它们属于同一个会话。

这种识别和维护会话状态的过程称为：

**会话跟踪。**

材料给出的定义是：

> 一种维护浏览器状态的方法，服务器需要识别多次请求是否来自同一浏览器，以便在同一次会话的多次请求之间共享数据。

# 5. 为什么需要会话跟踪

会话跟踪最核心的目的之一是：

> **让同一次会话中的多次请求能够共享数据。**

例如第一次登录成功时：

```text
用户 ID = 1
用户名 = admin
```

后续访问部门、员工等接口时，服务器仍然需要知道：

> 当前请求对应的是刚才登录成功的这个用户。

如果多次请求之间完全没有关联，就无法实现这种效果。

# 6. HTTP 是无状态协议

会话跟踪之所以需要额外实现，核心原因在于：

> **HTTP 是无状态协议。**

所谓无状态，是指：

> 每一次请求都是独立的，后一次请求不会自动知道前一次请求产生的数据。

材料中也明确指出，由于 HTTP 无状态，前一次请求生成的数据无法自动在后续请求中获得。

例如第一次请求：

```text
POST /login
```

登录成功。

第二次请求：

```text
GET /depts
```

如果没有额外机制，服务器无法仅凭第二次请求自动知道：

> 当前用户之前已经登录过。

# 7. 无状态带来的登录问题

对于登录认证来说，无状态会带来一个直接问题：

> 用户明明刚刚登录成功，但下一次请求到达服务器时，服务器仍然无法自动知道他的登录状态。

因此必须额外解决：

```text
登录成功的信息如何保存
后续请求如何携带这个信息
服务器如何识别这些请求属于同一个用户
```

这正是会话跟踪要解决的问题。

# 8. 会话跟踪的本质

可以把会话跟踪理解为：

> **给多次相互独立的 HTTP 请求建立关联。**

HTTP 请求本身仍然是无状态的。

会话跟踪并没有改变 HTTP 协议的这个特点。

它只是通过额外机制，在多次请求之间保存和传递某些状态数据。

因此，会话跟踪的核心目标是：

> 在无状态 HTTP 之上实现有状态的业务体验。

# 9. 会话中可以共享哪些数据

材料主要以登录认证为背景。

例如可以共享：

- 当前登录用户 ID
    
- 当前用户名
    
- 用户登录状态
    

第一次登录请求产生这些数据以后，后面的其他请求仍然需要使用。

因此，会话跟踪技术可以用于解决：

> **同一会话中的多次请求之间的数据共享问题。**

# 10. 常见会话跟踪方案

材料中介绍了三种会话跟踪方案：

```text
Cookie
Session
令牌技术
```

这三种方案都能够帮助服务器识别用户状态，但实现方式不同。

# 11. Cookie

Cookie 属于：

> **客户端会话跟踪技术。**

数据主要存储在浏览器客户端。

服务器向浏览器设置 Cookie 后，浏览器会保存这些数据，并在后续请求中携带 Cookie。

因此可以通过 Cookie 在多次请求之间传递信息。

具体机制会在：

```text

```

中单独整理。

# 12. Session

Session 属于：

> **服务端会话跟踪技术。**

会话数据主要存储在服务器端。

浏览器会保存一个用于识别 Session 的标识，后续请求携带这个标识，服务器再找到对应的 Session 数据。

具体机制会在：

```text
Session会话跟踪.md
```

中单独整理。

# 13. Token 令牌

令牌技术则通过：

> **一个代表用户身份的字符串**

来维护用户状态。

登录成功后，服务端生成令牌。

客户端保存令牌，并在后续请求中携带。

服务器通过校验令牌来判断用户身份。

具体机制会在：

```text
Token令牌认证.md
```

中单独整理。

# 14. 三种方案的基本区别

可以先从数据保存位置理解三种方案。

|方案|状态数据主要保存位置|
|---|---|
|Cookie|浏览器客户端|
|Session|服务器端|
|Token|身份信息封装在令牌中，由客户端保存并携带|

当前阶段不需要深入它们的优缺点，只需要理解：

> 三种方案的目标都是让服务器在多次请求之间识别用户状态。

# 15. 会话技术与登录认证的关系

会话技术并不只用于登录认证。

但是登录认证是它最典型的使用场景之一。

用户登录成功之后，需要让后续请求继续保留：

> 已经登录成功的身份状态。

因此登录认证通常需要结合某种会话跟踪方案。

在当前材料中，最终采用的是：

```text
令牌技术
```

来完成这个任务。

# 16. 会话跟踪与统一拦截的区别

这两个概念容易混淆。

## 16.1 会话跟踪

解决的是：

> 当前用户是谁，以及如何在多次请求之间维持身份状态。

## 16.2 统一拦截

解决的是：

> 请求到达业务接口之前，是否需要先检查用户身份。

因此：

```text
会话跟踪
负责保存和传递身份信息

统一拦截
负责检查身份信息是否合法
```

两者配合后，才能实现完整登录校验。

# 17. 当前阶段需要掌握的核心内容

1. 会话是浏览器与服务器之间的一次交互过程。
    
2. 一次会话中可以包含多次请求和响应。
    
3. 会话与浏览器有关，不同浏览器通常对应不同会话。
    
4. 会话跟踪用于识别多次请求是否来自同一个浏览器。
    
5. 会话跟踪的主要目的之一是实现多次请求之间的数据共享。
    
6. HTTP 是无状态协议，每一次请求默认彼此独立。
    
7. 因为 HTTP 无状态，登录状态不会自动延续到后续请求。
    
8. 会话跟踪通过额外机制在多次 HTTP 请求之间维护状态。
    
9. 常见会话跟踪方案有 Cookie、Session 和令牌技术。
    
10. Cookie 主要在客户端保存数据。
    
11. Session 主要在服务端保存数据。
    
12. Token 通过身份令牌在客户端和服务端之间传递身份信息。
    
13. 会话跟踪负责维护身份状态，统一拦截负责校验身份状态。
    

> [!tip] 一句话总结
> 
> `会话跟踪是在 HTTP 无状态的基础上，通过 Cookie、Session 或 Token 等机制识别同一浏览器的多次请求，并实现同一次会话中状态数据的共享。`
