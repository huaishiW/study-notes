# 1. 什么是 Token

Token 中文通常称为：

**令牌**

材料中对 Token 的描述很直接：

> Token 本质上就是一个表示用户身份的字符串。

也就是说，Token 的核心作用是：

> **作为用户身份的标识。**

当用户登录成功之后，服务器生成一个 Token。

之后客户端每次访问受保护资源时，都需要携带这个 Token。

服务器通过校验 Token 来判断：

> 当前请求是否来自一个已经登录成功的用户。

# 2. 为什么需要 Token

前面已经学习了两种传统的会话跟踪方案：

```text
Cookie
Session
```

它们都可以实现多次请求之间的状态共享。

但是材料指出，在现代企业项目中，这两种方案存在一些明显限制。

例如：

- Cookie 在移动端使用受限
    
- Cookie 存在跨域问题
    
- Session 依赖 Cookie
    
- Session 在服务器集群环境下无法直接使用
    

因此，材料进一步引出了：

```text
Token
```

令牌技术。

# 3. Token 的基本工作思路

使用 Token 进行会话跟踪时，可以分成两个阶段。

## 3.1 登录成功后生成 Token

用户首先发送登录请求。

如果用户名和密码正确：

> 服务器生成一个 Token。

这个 Token 就代表：

> 当前用户已经通过身份验证。

然后服务器将 Token 返回给前端。

## 3.2 前端保存 Token

前端拿到 Token 后，需要把它保存起来。

材料中提到，可以保存到：

```text
Cookie
localStorage
```

等客户端存储空间中。

## 3.3 后续请求携带 Token

在后续每一次请求中：

> 客户端都需要把 Token 携带到服务端。

服务端收到请求后，再对 Token 进行校验。

## 3.4 服务端校验 Token

服务器接收到 Token 后，需要判断它是否有效。

如果 Token 有效：

> 说明用户已经登录，可以继续访问业务接口。

如果 Token 无效：

> 说明当前身份不合法，应拒绝访问。

因此，Token 实现登录认证的关键就在于：

```text
生成 Token
携带 Token
校验 Token
```

# 4. Token 中可以携带数据

材料中指出：

> 如果需要在同一次会话的多次请求之间共享数据，可以把需要共享的数据存储到 Token 中。

例如可以保存：

```text
用户 ID
用户名
```

这样后续服务端解析 Token 时，就可以重新获取这些身份信息。

# 5. Token 与 Session 的核心区别

Session 的主要特点是：

> 用户状态数据保存在服务器端。

而 Token 的思路是：

> 用户身份信息由 Token 表示，并由客户端保存和携带。

因此二者最大的区别之一在于：

```text
Session
服务端保存状态

Token
客户端保存并携带身份令牌
```

材料也因此指出，Token 不需要服务器端保存大量会话数据，可以减轻服务器存储压力。

# 6. Token 为什么适合服务器集群

Session 在集群环境中的问题是：

> Session 默认保存在某一台服务器中。

如果下一次请求被负载均衡分发到另一台服务器，就可能找不到原来的 Session。

而 Token 不依赖某一台服务器保存用户会话状态。

客户端每一次请求都会直接携带 Token。

只要不同服务器都具备相同的 Token 校验能力，就可以直接验证用户身份。

因此材料指出：

> Token 可以解决服务器集群环境下的认证问题。

# 7. Token 为什么适合移动端

材料中指出，Token 支持：

```text
PC 端
移动端
```

相比依赖浏览器 Cookie 自动机制的方案，Token 可以由客户端程序主动保存和主动携带。

因此，在 Android、iOS 等客户端场景中也可以使用。

# 8. Token 可以减轻服务器存储压力

使用 Session 时，服务器需要维护大量用户的 Session 数据。

用户越多：

> 服务端需要保存的会话状态也越多。

而 Token 方案中，身份信息主要封装在令牌中，并由客户端保存。

因此服务器不需要为每个用户维护对应的会话对象。

材料把这一点概括为：

> 减轻服务器存储压力。

# 9. Token 的优点

材料中列出的主要优点包括：

- 支持 PC 端
    
- 支持移动端
    
- 解决集群环境下的认证问题
    
- 减轻服务器存储压力
    

这些特点使 Token 更适合现代前后端分离项目。

# 10. Token 的缺点

材料中也指出：

> Token 相关功能需要开发者自己实现。

包括：

- Token 的生成
    
- Token 的传递
    
- Token 的校验
    

也就是说，浏览器不会像 Cookie 那样自动帮助完成整套认证逻辑。

开发者需要自己定义：

> Token 如何生成、放在哪里、每次请求如何携带，以及服务端如何校验。

# 11. 为什么当前项目最终选择 Token

材料在 Cookie、Session、Token 三种方案对比之后明确指出：

> 当前企业项目中，更常使用令牌技术进行会话跟踪。

当前案例也最终采用 Token 方案来解决登录认证问题。

原因主要包括：

- 适合前后端分离
    
- 支持移动端
    
- 适合集群部署
    
- 服务端无需保存大量 Session
    

# 12. Token 在登录认证中的典型过程

材料随后进一步给出了 Token 登录认证的典型流程。

用户首先访问：

```text
/login
```

如果登录成功：

> 服务器生成 Token 并返回给前端。

前端保存 Token 后，在后续每次请求中都携带 Token。

服务端统一拦截这些请求：

- 没有 Token → 拒绝访问
    
- Token 无效 → 拒绝访问
    
- Token 有效 → 放行请求
    

# 13. Token 登录认证中的两个核心操作

材料将整个 Token 登录认证过程总结为两个核心步骤。

## 13.1 生成令牌

在用户登录成功之后：

> 生成一个 Token，并返回给前端。

## 13.2 校验令牌

后续每一次请求中：

> 服务端接收 Token，并对 Token 进行校验。

因此后续真正实现登录认证时，主要就是围绕：

```text
生成
校验
```

这两个动作展开。

# 14. Token 与 JWT 的关系

Token 是一个更大的概念。

它表示：

> 用来证明用户身份的令牌机制。

而当前材料后续采用的具体 Token 形式是：

```text
JWT
```

也就是：

```text
JSON Web Token
```

因此可以理解为：

```text
Token
是一种认证思路

JWT
是 Token 的一种具体实现形式
```

当前这一篇重点理解 Token 机制本身。

JWT 的结构、签名和生成校验会在后续笔记中单独整理。

# 15. Cookie、Session、Token 简单对比

|方案|主要状态位置|是否依赖服务端会话状态|集群适应性|
|---|---|---|---|
|Cookie|客户端|否|较好|
|Session|服务端|是|默认存在问题|
|Token|客户端携带令牌|否|较好|

当前材料最终选择：

```text
Token
```

作为登录认证的会话跟踪方案。
