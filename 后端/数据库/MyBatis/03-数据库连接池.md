# 1. 为什么需要数据库连接池

在没有数据库连接池的情况下，每一次执行 SQL 都需要：

1. 创建一个新的数据库连接。
    
2. 使用该连接执行 SQL。
    
3. SQL 执行完成后关闭连接。
    

也就是说，每一次数据库操作都会重复经历：

- 创建 `Connection`
    
- 使用 `Connection`
    
- 销毁 `Connection`
    

数据库连接的创建和销毁都需要消耗系统资源。

如果应用程序频繁访问数据库，那么不断重复创建和销毁连接，会带来较大的性能开销。

因此，需要一种机制来：

> 统一管理数据库连接，并让已经创建的连接可以重复使用。

这就是数据库连接池存在的原因。

---

# 2. 数据库连接池是什么

数据库连接池可以理解为：

> 一个专门负责分配和管理数据库连接 `Connection` 的容器。

程序启动后，连接池会提前创建一定数量的数据库连接。

当程序需要访问数据库时，不再重新创建连接，而是：

1. 从连接池中获取一个已有的 `Connection`。
    
2. 使用该连接执行 SQL。
    
3. SQL 执行完成后，将连接归还给连接池。
    

这个连接并不会立即被销毁，而是可以继续被后续数据库操作重复使用。

---

# 3. 没有连接池时的工作方式

如果不使用数据库连接池，一次数据库操作通常是：

1. 程序需要访问数据库。
    
2. 创建新的 `Connection`。
    
3. 使用 `Connection` 执行 SQL。
    
4. SQL 执行完成。
    
5. 关闭 `Connection`。
    
6. 下一次访问数据库时，再重新创建一个新的 `Connection`。
    

这种方式的问题在于：

> 每一次数据库操作都需要创建和销毁连接。

当访问量比较大时，这种频繁操作会浪费大量系统资源。

这里将这一问题概括为：

> 每次执行 SQL 都创建连接、销毁连接，这种频繁重复创建和销毁的过程比较耗费计算机性能。

---

# 4. 使用连接池后的工作方式

使用数据库连接池后，程序启动时会提前创建一定数量的 `Connection`。

当程序需要执行 SQL 时：

1. 从数据库连接池获取一个 `Connection`。
    
2. 使用这个连接执行 SQL。
    
3. SQL 执行完成后释放连接。
    
4. 这里的“释放”并不是销毁连接。
    
5. 而是将连接重新归还到连接池。
    
6. 后续其他数据库操作可以继续使用这个连接。
    

因此：

> 数据库连接从“一次性创建和销毁”变成了“重复复用”。

这也是连接池提高性能的核心原因。

---

# 5. 连接池中的 Connection 是如何复用的

数据库连接池中的 `Connection` 可以被多个数据库操作重复使用。

例如：

第一次数据库操作：

- 从连接池获取连接 A。
    
- 使用连接 A 执行 SQL。
    
- 执行结束后归还连接 A。
    

第二次数据库操作：

- 又可以从连接池获取连接 A。
    
- 再次使用连接 A。
    
- 使用完成后再次归还。
    

因此，程序不需要每次都重新建立数据库连接。

连接池真正管理的是：

> 已经创建好的数据库连接资源。

这样可以避免频繁创建和销毁 `Connection`。

---

# 6. 连接归还不等于真正关闭

使用原生 JDBC 时：

```java
conn.close();
```

通常理解为关闭数据库连接。

但在使用数据库连接池时，连接的“关闭”更接近：

> 将连接归还给连接池。

也就是说，程序使用结束之后，不再继续占用该连接，但连接本身可以继续被连接池管理和复用。

从使用者角度看，依然需要正常释放连接。

但从连接池角度看，这个连接不一定真正销毁，而是重新进入可用状态。

---

# 7. 连接池为什么还会真正释放连接

数据库连接池虽然会复用连接，但并不是所有连接都会永久存在。

这里注意：

> 如果连接长时间处于空闲状态，并且超过连接池设置的最大空闲时间，连接池会自动释放该连接。

例如：

1. 一个 `Connection` 被创建。
    
2. 当前没有任何 SQL 使用它。
    
3. 它长时间处于空闲状态。
    
4. 空闲时间超过连接池配置的最大空闲时间。
    
5. 连接池自动释放这个连接。
    

这样可以避免：

> 无效连接长期占用数据库和系统资源。

---

# 8. 数据库连接池的三个主要有点

## 8.1 资源重用

数据库连接可以重复使用。

不需要每执行一次 SQL 就重新创建连接。

因此可以减少大量重复的资源创建和销毁操作。

---

## 8.2 提升系统响应速度

因为连接已经提前创建好，程序访问数据库时可以直接从连接池获取连接。

不需要每次等待数据库连接重新建立。

因此可以提升数据库访问效率和系统响应速度。

---

## 8.3 避免数据库连接遗漏

数据库连接由连接池统一管理。

连接池可以自动处理部分连接生命周期问题，例如释放长时间空闲的连接。

从而减少由于连接未正确释放而导致的资源问题。

---

# 9. DataSource 是什么

Java 官方为数据库连接池定义了一套统一标准。

这个标准就是：

```java
javax.sql.DataSource
```

`DataSource` 是数据库连接池相关的标准接口。其中第三方数据库连接池也需要按照 `DataSource` 接口进行实现。

---

# 10. DataSource 的核心作用

`DataSource` 最核心的功能是：

> 获取数据库连接。

其中有一个重要方法：

```java
public Connection getConnection() throws SQLException;
```

也就是说，应用程序可以通过 `DataSource` 获取：

```java
Connection
```

而不需要自己直接调用：

```java
DriverManager.getConnection(...)
```

因此可以简单理解为：

> `DataSource` 是 Java 为数据库连接池定义的统一接口。

不同连接池产品负责实现这个接口。

---

# 11. 为什么需要 DataSource 标准

如果没有统一标准，每一种数据库连接池可能都有完全不同的使用方式。

Java 官方定义：

```java
DataSource
```

接口之后，不同第三方连接池都按照统一标准实现。

例如：

- Hikari 实现 `DataSource`
    
- Druid 实现 `DataSource`
    
- C3P0 实现 `DataSource`
    
- DBCP 实现 `DataSource`
    

这样应用程序就不需要完全依赖某一个连接池的具体实现方式。

核心思想是：

> Java 定义标准接口，第三方连接池产品提供具体实现。

---

# 12. 常见数据库连接池

这里列出了几种常见数据库连接池：

- C3P0
    
- DBCP
    
- Druid
    
- Hikari
    

其中目前使用较多的是：

- Hikari
    
- Druid
    

这两种连接池的性能相对更加优秀。

---

# 13. Hikari

Hikari 是 Spring Boot 默认使用的数据库连接池。

在 Spring Boot 项目中，如果没有额外切换数据库连接池，底层默认通常使用：

```text
Hikari
```

也可以通过控制台日志说明这就是默认的连接池：

> Spring Boot 默认使用的数据库连接池就是 Hikari。

---

# 14. Hikari 的特点

在当前阶段，需要掌握的重点主要是：

> Hikari 是 Spring Boot 默认使用的数据库连接池。

也就是说，在使用：

```properties
spring.datasource.url=...
spring.datasource.username=...
spring.datasource.password=...
```

配置数据库后，即使没有手动指定某一个连接池，也可以直接使用数据库连接池能力。

Spring Boot 会使用默认的 Hikari 连接池管理数据库连接。

---

# 15. Druid

Druid 是阿里巴巴开源的一款数据库连接池。它的功能强大、性能优秀、同时提供了很多方便的功能是 Java 中常用的数据库连接池之一

Druid 和 Hikari 都可以用于管理数据库连接。

它们都解决的是同一个核心问题：

> 数据库连接的创建、复用、分配和释放。

---

# 16. Spring Boot 默认为什么不是必须手动配置连接池

在 Spring Boot 项目中，通常只需要配置：

```properties
spring.datasource.url=jdbc:mysql://localhost:3306/web
spring.datasource.username=root
spring.datasource.password=1234
```

项目就可以使用数据库连接池。

原因是：

> Spring Boot 已经默认集成了 Hikari。

因此不需要额外手动创建：

```java
DataSource
```

也不需要自己管理连接池对象。

这也是 Spring Boot 自动配置带来的便利。

---

# 17. 如何切换为 Druid

如果不想使用 Spring Boot 默认的 Hikari，而是希望使用 Druid，需要进行配置。

---

## 17.1 第一步：引入 Druid 依赖

在 `pom.xml` 中加入 Druid 依赖：

```xml
<dependency>
    <groupId>com.alibaba</groupId>
    <artifactId>druid-spring-boot-starter</artifactId>
    <version>1.2.19</version>
</dependency>
```

这个依赖用于：

> 将 Druid 数据库连接池集成到 Spring Boot 项目中。

---

## 17.2 第二步：配置 Druid 数据源

在：

```text
application.properties
```

中指定 Druid：

```properties
spring.datasource.type=com.alibaba.druid.pool.DruidDataSource

spring.datasource.druid.driver-class-name=com.mysql.cj.jdbc.Driver

spring.datasource.druid.url=jdbc:mysql://localhost:3306/web

spring.datasource.druid.username=root

spring.datasource.druid.password=1234
```

其中：

```properties
spring.datasource.type=com.alibaba.druid.pool.DruidDataSource
```

用于指定：

> 当前项目使用 Druid 作为数据库连接池。

---

# 18. Hikari 与 Druid 的关系

Hikari 和 Druid 都属于：

> 数据库连接池产品。

它们的基本职责是相同的：

- 创建数据库连接。
    
- 管理数据库连接。
    
- 分配数据库连接。
    
- 回收数据库连接。
    
- 复用数据库连接。
    

区别在于：

> 它们是不同组织提供的不同连接池实现。

当前阶段主要需要记住：

- Spring Boot 默认使用 Hikari。
    
- Druid 是阿里巴巴开源的连接池。
    
- 如果需要，可以通过依赖和配置将 Hikari 切换为 Druid。
    

---

# 19. DataSource、Hikari、Druid 的关系

这几个概念容易混淆。

可以这样理解。

## 19.1 DataSource

`DataSource` 是：

> Java 官方定义的数据库连接池标准接口。

它定义数据库连接池应该具有什么基本能力。

例如：

```java
Connection getConnection();
```

---

## 19.2 Hikari

Hikari 是：

> `DataSource` 标准的一种具体数据库连接池实现。

同时也是 Spring Boot 默认使用的连接池。

---

## 19.3 Druid

Druid 是：

> `DataSource` 标准的另一种数据库连接池实现。

由阿里巴巴开源。

---

因此三者不是同一个层级的概念。

`DataSource` 是标准。

Hikari 和 Druid 是具体产品和实现。

---

# 20. 数据库连接池与 MyBatis

MyBatis 使用数据库连接池后，可以避免原生 JDBC 中：

> 每次访问数据库都重新创建和销毁连接。

原生 JDBC 中，开发者可能直接：

```java
Connection conn =
    DriverManager.getConnection(...);
```

然后执行完 SQL 后：

```java
conn.close();
```

而在 MyBatis 中，数据库连接可以由连接池统一管理。

开发者调用 Mapper：

```java
userMapper.findAll();
```

时，并不需要自己手动创建 `Connection`。

MyBatis 会从数据源中获取连接并完成数据库操作。

因此将数据库连接池视为 MyBatis 相比原生 JDBC 的一个重要改进。

# 22. 不要把连接池理解成数据库

数据库连接池本身并不是数据库。

MySQL 才是真正负责：

- 存储数据。
    
- 执行 SQL。
    
- 返回查询结果。
    

连接池只是负责管理：

```java
Connection
```

对象。

也就是说：

> 连接池管理的是“应用程序如何连接数据库”，而不是“数据库中的数据”。

---

# 23. 不要把 DataSource 理解成某一种连接池

`DataSource` 并不是 Hikari，也不是 Druid。

`DataSource` 是一个：

> 标准接口。

而：

- Hikari
    
- Druid
    

是这个标准的具体实现。

因此应该区分：

```text
DataSource：规范

Hikari：实现

Druid：实现
```

---

# 24. 连接池真正解决的问题

数据库连接池并不是为了简化 SQL。

SQL 仍然由 MyBatis 或 JDBC 执行。

连接池真正解决的是：

> 数据库连接资源的管理问题。

核心问题包括：

- 避免频繁创建连接。
    
- 避免频繁销毁连接。
    
- 复用已有连接。
    
- 统一管理连接生命周期。
    
- 提升数据库访问效率。
    

因此连接池关注的是：

```text
Connection
```

而不是具体：

```sql
SELECT
INSERT
UPDATE
DELETE
```

语句。
